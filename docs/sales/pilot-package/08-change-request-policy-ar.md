# سياسة طلبات التغيير خلال Pilot

الحالة: مسودة تشغيلية  
الاستخدام: ضبط أي طلب يظهر أثناء Pilot حتى لا يتوسع النطاق دون قرار

## الهدف

حماية نجاح Pilot من التوسع غير المنضبط. ليس كل طلب جديد يرفض، لكن كل طلب يجب أن يسجل ويقيم قبل التنفيذ.

## 1. تعريف طلب التغيير

طلب التغيير هو أي طلب لا يدخل بوضوح في نطاق Pilot المعتمد، مثل:

1. إضافة موقع جديد.
2. إضافة عدد كبير من الأصول أو المستخدمين.
3. تعديل مسار الاعتماد بشكل جوهري.
4. بناء تقرير جديد.
5. تكامل مع نظام خارجي.
6. واتساب رسمي أو تطبيق جوال.
7. تخصيص واجهة أو كود.
8. تنظيف بيانات إضافي.

## 2. خطوات التعامل

| الخطوة | الإجراء | المسؤول |
| --- | --- | --- |
| التسجيل | تسجيل الطلب في قائمة موحدة | متقن أو مالك Pilot |
| التوضيح | فهم المشكلة التي يحاول الطلب حلها | متقن والعميل |
| التصنيف | Bug، إعداد، تدريب، تحسين، توسع، تكامل | متقن |
| تقييم الأثر | أثره على الوقت والسعر ونجاح Pilot | متقن |
| القرار | تنفيذ، تأجيل، تسعير مستقل، أو رفض | صاحب القرار ومتقن |
| التوثيق | كتابة القرار وسببه | متقن |

## 3. تصنيفات الطلبات

| التصنيف | الوصف | القرار الافتراضي |
| --- | --- | --- |
| Bug | عطل في وظيفة ضمن النطاق | يعالج ضمن الدعم |
| إعداد | تغيير بسيط في بيانات أو صلاحيات | ينفذ إذا كان موثقا ولا يوسع النطاق |
| تدريب | سؤال أو سوء فهم من المستخدم | يعالج بتوجيه |
| تحسين صغير | تعديل مفيد لكنه غير مانع | يؤجل غالبا، ولا ينفذ داخل Pilot إلا إذا كان بسيطا وموثقا ولا يخلق التزاما مستمرا |
| توسع نطاق | إضافة موقع، فريق، أصول كثيرة، مستخدمين كثيرين | يؤجل أو يسعر |
| تقرير مخصص | مؤشر أو تقرير غير موجود | يقيم بعد Pilot غالبا |
| تكامل | ربط نظام خارجي | خارج Pilot |
| تغيير منتج | ميزة جديدة أو تعديل كود كبير | خارج Pilot |

## 5. متى ينفذ الطلب داخل Pilot؟

يمكن تنفيذ الطلب إذا:

1. كان داخل النطاق الأصلي.
2. أو كان إعدادا بسيطا وموثقا لا يغير الوعود.
3. أو كان يعالج عطلا حقيقيا يمنع استخدام المسار.
4. أو كان تحسينه ضروريا لإنقاذ Pilot دون فتح التزام دائم، وبموافقة متقن وصاحب القرار.

## 6. متى يؤجل لما بعد Pilot؟

يؤجل الطلب إذا:

1. لا يمنع إثبات القيمة الأساسية.
2. يحتاج وقتا أو تنسيقا أكبر من مدة Pilot.
3. يتعلق بتقارير أو تكاملات أو توسع مواقع.
4. لا توجد بيانات كافية لتصميمه الآن.
5. يفضل بناؤه بعد فهم استخدام العميل الحقيقي.

## 7. متى يسعر بشكل مستقل؟

يسعر الطلب بشكل مستقل إذا:

1. يضيف عملا واضحا خارج العرض.
2. يتطلب إعدادات أو بيانات أو تدريب إضافي.
3. يحتاج تطويرا أو تكاملا أو تقريرا خاصا.
4. يوسع عدد المواقع أو المستخدمين أو الأصول بشكل كبير.
5. يطلب من متقن القيام بأعمال تشغيلية نيابة عن العميل.

## 8. متى يرفض؟

يرفض الطلب إذا:

1. يهدد نجاح Pilot أو يؤخر التشغيل.
2. يخلق وعدا غير جاهز للبيع.
3. يحول متقن إلى شركة تشغيل ميداني بدلا من نظام.
4. يتطلب دعما 24/7 غير متفق عليه.
5. يطلب "كل شيء غير محدود" ضمن سعر محدود.
6. يخالف حدود المنتج أو الأمان أو طريقة التشغيل.

## صياغة آمنة للعميل

نرحب بتسجيل طلبات التحسين أثناء Pilot، لكن تنفيذها يعتمد على النطاق والأثر. الهدف من Pilot إثبات قيمة المسار الأساسي أولا، ثم ترتيب التوسعات بناء على بيانات حقيقية.
