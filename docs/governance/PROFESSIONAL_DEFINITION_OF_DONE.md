# معيار متقن للاكتمال المهني

**الاسم الإنجليزي:** Mutqan Professional Definition of Done

**الحالة:** معيار حاكم للتنفيذ والمراجعة والإطلاق

**النطاق:** المنتج، الخدمة، البيانات، المستندات، العلامة، التسويق، والتشغيل

**قاعدة حاكمة:** عمل الكود أو جمال الشاشة وحده لا يعني أن العمل مكتمل.

## 1. الغرض

يحدد هذا المعيار معنى أن تكون قدرة أو رحلة أو مادة في متقن «مكتملة مهنيًا».
لا يجوز وصف أي عمل بأنه منتهٍ ما لم يثبت أنه:

1. يحل احتياجًا ذا أولوية ومحدد النطاق؛
2. يعمل بصورة صحيحة وآمنة ضمن نموذج السلطة والصلاحيات؛
3. يصلح للأدوار والأجهزة واللغات التي يستهدفها؛
4. يحافظ على جودة البيانات وقابلية التتبع؛
5. يقدم تجربة متقنة بصريًا ولغويًا دون إضعاف الوضوح أو الأداء؛
6. يمكن تشغيله ودعمه وقياسه؛
7. لا ينتج ادعاءً تسويقيًا يتجاوز الدليل؛
8. اجتاز بوابات البيئة المناسبة قبل الوصول إلى العميل.

هذا المعيار لا يمنح تلقائيًا أي اعتماد خارجي. لا تستخدم عبارة «معتمد من هيئة
كفاءة الإنفاق» أو «مطابق للدليل الوطني لإدارة الأصول والمرافق» إلا بوجود
إثبات اعتماد رسمي مكتوب يجيز العبارة والنطاق. يجوز استخدام وصف مواءمة محدود
فقط إذا كان مدعومًا بمصفوفة تتبع منشورة داخليًا ومراجعة معتمدة.

## 2. حالات الاكتمال

| الحالة | المعنى | الحد الأدنى |
| --- | --- | --- |
| قيد الاكتشاف | الاحتياج والنطاق لم يثبتا بعد | فرضية، أسئلة بحث، ومالك |
| جاهز للتنفيذ | المشكلة ومعيار النجاح ونطاق السلطة معتمدة | بوابة القيمة وخطة الأدلة |
| منفذ | التنفيذ موجود محليًا لكنه لم يثبت في بيئة مماثلة | مراجعة الكود والاختبارات المحلية |
| جاهز لـ Staging | بوابات 1–13 مكتملة أو مستثناة رسميًا | ملف أدلة قابل للمراجعة |
| مثبت على Staging | رحلة حقيقية واختبارات خصومية وأدلة تشغيل ناجحة | بوابة Staging مكتملة |
| جاهز لمراجعة Production | لا توجد شروط توقف مفتوحة وخطة نشر/استعادة معتمدة | بوابة Production قبل أول كتابة |
| مكتمل مهنيًا | نُشر بتفويض منفصل، واجتاز التحقق اللاحق ونافذة المراقبة المحددة | دليل الإنتاج ومراجعة النتيجة |

لا تعني عبارة «جاهز لمراجعة Production» الإذن بالنشر. النشر يحتاج تفويضًا
صريحًا منفصلًا وهوية مشغل ونافذة تغيير محددة.

## 3. مالكو البوابات

يجوز أن يؤدي شخص واحد أكثر من دور في المرحلة الحالية، لكن لا يجوز أن يعتمد
المنفذ وحده بوابته عالية الخطورة.

| الرمز | الدور | المسؤولية |
| --- | --- | --- |
| `PO` | مالك المنتج/المؤسس | أولوية المشكلة، نطاق القيمة، والقرار التجاري النهائي |
| `DOMAIN` | مراجع إدارة المرافق/الأصول | صحة الإجراء والمصطلح والنموذج التشغيلي |
| `ENG` | مالك الهندسة | التصميم التقني، الاختبارات، الأداء، وقابلية الصيانة |
| `SEC` | مراجع الأمن والسلطة | الصلاحيات، العزل، الخصوصية، ونمذجة إساءة الاستخدام |
| `UX` | مالك تجربة المستخدم | رحلات الأدوار، قابلية الاستخدام، الوصول، والاستجابة |
| `CONTENT` | مالك المحتوى العربي/الإنجليزي | المصطلحات، النبرة، الترجمة، والتعليمات |
| `CRAFT` | المراجع البصري/العلامة | الحرفة، الاتساق، الحركة، واللحظات المميزة |
| `DATA` | مالك البيانات والتحليلات | جودة البيانات، القياس، النسب، والتتبع |
| `OPS` | مالك التشغيل والدعم | المراقبة، الاستعادة، إجراءات الدعم، والاستمرارية |
| `GROWTH` | مالك التسويق/المبيعات | صحة الادعاءات والأصول التجارية وتجربة ما قبل البيع |
| `REL` | مشغل الإصدار | هوية النسخة، البيئة، runbook، والتنفيذ المراقب |

## 4. قواعد الدليل

كل علامة قبول في القوائم التالية تحتاج دليلًا. لا تقبل عبارات مثل «جُرّب»،
«يبدو جيدًا»، أو «المفترض يعمل».

### 4.1 سجل الدليل الإلزامي

يسجل لكل قدرة أو رحلة:

- معرف العمل واسم الرحلة ونطاقها وما هو خارج النطاق؛
- المالك والمراجعين وتاريخ القرار؛
- Git commit/tag والملفات أو الإعدادات المتأثرة؛
- البيئة ومرجع المشروع/النشر ونسخة قاعدة البيانات؛
- نسخة الاختبار، نوع البيانات، الأدوار، الجهاز، المتصفح واللغة؛
- النتيجة المتوقعة والفعلية مع أثر زمني؛
- رابط الاختبار أو التقرير أو التسجيل أو الاستعلام؛
- العيوب المفتوحة ودرجة خطورتها وقرارها؛
- القياس قبل/بعد وحدود العينة؛
- تاريخ انتهاء صلاحية الدليل إذا كان قابلًا للتقادم.

### 4.2 قوة الدليل

| الدرجة | مثال | استخدامه |
| --- | --- | --- |
| `E0` | رأي أو لقطة بلا سياق | لا يثبت القبول |
| `E1` | فحص ثابت أو اختبار محلي معزول | يدعم التنفيذ، لا يثبت الرحلة |
| `E2` | اختبار آلي قابل للتكرار أو مراجعة موثقة | يثبت شرطًا محددًا |
| `E3` | رحلة حقيقية على Staging ببيانات وأدوار ممثلة | مطلوب للمسارات الحرجة |
| `E4` | قياس إنتاجي أو Pilot موثق مع حدود العينة | يثبت الأثر الفعلي |
| `E5` | تحقق مستقل أو اعتماد رسمي محدد النطاق | للادعاءات الخارجية المنظمة |

لقطة الشاشة قد تكون جزءًا من الدليل، لكنها لا تستبدل سجل البيئة والهوية
والنتيجة القابلة للتكرار. نتائج metadata وحدها لا تستبدل fixture فعليًا.

## 5. ملف قبول العمل

قبل بدء التنفيذ ينشأ سجل قصير بهذه الحقول:

| الحقل | المطلوب |
| --- | --- |
| المشكلة | سلوك أو تكلفة أو خطر محدد، وليس اسم ميزة |
| المستفيد والأدوار | من يتأثر مباشرة ومن يراجع أو يعتمد |
| الدليل الحالي | مقابلة، مشاهدة ميدانية، بيانات استخدام، طلب عميل، معيار، أو حادثة |
| الفرضيات | ما لم يثبت بعد وكيف سيختبر |
| معيار النجاح | نتيجة قابلة للقياس أو قرار ثنائي واضح |
| النطاق وخارجه | ما ستغطيه النسخة وما لن تدعيه |
| خريطة السلطة | من يقرأ وينشئ ويعدل ويعتمد ويتجاوز، وفي أي حالة |
| ميزانية الجودة | الأداء، الوصول، البيانات، الوثائق، والدعم المطلوبة |
| خطة القياس | الأحداث، المقاييس، خط الأساس، العينة، ومدة الملاحظة |
| خطة التراجع | طريقة الإيقاف أو الرجوع وحفظ البيانات |

غياب المشكلة أو معيار النجاح أو خريطة السلطة يمنع بدء التنفيذ عالي التأثير.

## 6. بوابات الاكتمال المهني

### G1 — القيمة والاحتياج الفعلي

| قائمة التحقق | المالك | دليل القبول | شرط التوقف |
| --- | --- | --- | --- |
| المشكلة موصوفة بلغة عمل العميل وليست حلًا مفترضًا | `PO` + `DOMAIN` | سجل اكتشاف يذكر المصدر والتاريخ | لا يوجد مصدر للمشكلة |
| حدد الدور والسياق والتكرار وشدة الأثر | `PO` | مقابلات/ملاحظة/بيانات مع حدود العينة | شريحة أو دور مجهول |
| البدائل الحالية معروفة، بما فيها الإجراء اليدوي وعدم الفعل | `PO` | مقارنة سير عمل لا مقارنة قوائم مزايا | لم تدرس طريقة العمل الحالية |
| معيار النجاح وخط الأساس محددان قبل البناء | `PO` + `DATA` | بطاقة قياس مع تعريف البسط والمقام | نجاح غير قابل للقياس |
| المتطلب النظامي أو الدليلي مصنف: ملزم، إرشادي، أو غير منطبق | `DOMAIN` | مرجع إصدار ونطاق ومصفوفة تتبع | ادعاء امتثال بلا مرجع ونطاق |
| قيمة العمل تبرر تكلفة البناء والتشغيل والدعم | `PO` + `OPS` | تقدير منفعة/تكلفة ومخاطر | لا يوجد مالك أو قدرة تشغيلية |

### G2 — سلامة الوظيفة والسلطة

| قائمة التحقق | المالك | دليل القبول | شرط التوقف |
| --- | --- | --- | --- |
| المسار السعيد وحالات الخطأ والإلغاء وإعادة المحاولة محددة | `ENG` + `UX` | سيناريوهات قبول آلية ويدوية | حالة فشل صامتة أو نتيجة ملتبسة |
| انتقالات الحالة تمنع القفز والتكرار والتعارض | `ENG` | اختبارات state transition وidempotency | ازدواج أو انتقال غير مشروع |
| السلطة صريحة ومركزية وتتحقق على الخادم/قاعدة البيانات | `ENG` + `SEC` | مصفوفة role/action واختبارات خصومية | اعتماد على إخفاء الواجهة فقط |
| المستخدم غير النشط أو الموقوف يمنع مركزيًا | `SEC` | fixture لحساب نشط وغير نشط وموقوف | مسار يتجاوز authority المركزية |
| العزل بين المؤسسات يثبت ببيانات Tenant A وTenant B | `SEC` | اختبار قراءة وكتابة وتعديل عابر للمؤسسات | أي رؤية أو تأثير عابر للمؤسسات |
| المسارات الحساسة deny-by-default مع allowlist محددة | `SEC` | ACL/RLS/function-grant diff وfixture | صلاحية ضمنية أو fail-open |
| `SECURITY DEFINER` عند الضرورة فقط، مع `search_path` وgrants آمنة | `SEC` | فحص التعريف والاستدعاء لكل دور | استدعاء مجهول أو دور غير مقصود |
| التزامن وإعادة التشغيل لا يكرران الدفع أو التوفير أو أمر العمل | `ENG` | اختبار concurrent/idempotent replay | نتيجتان لنفس المرجع أو تضارب صامت |
| سجل التدقيق يجيب: من، ماذا، متى، من أين، ولماذا | `ENG` + `DATA` | استعلام أثر من الفعل إلى السجل | تغيير حساس بلا أثر |

### G3 — تجربة الأدوار وسير العمل

| قائمة التحقق | المالك | دليل القبول | شرط التوقف |
| --- | --- | --- | --- |
| رحلة مستقلة لكل دور داخل النطاق، لا شاشة واحدة للجميع | `UX` + `DOMAIN` | role journey map واختبار لكل دور | دور لا يستطيع إكمال مهمته الأساسية |
| الأولوية والإجراء التالي واضحان دون معرفة داخلية | `UX` | اختبار task success وملاحظة الاستخدام | يحتاج المستخدم شرحًا شفهيًا دائمًا |
| الشاشات الفارغة والخطأ والتحميل والمنع والانقطاع مصممة | `UX` + `ENG` | حالات مرئية ومختبرة | شاشة بيضاء أو رسالة تقنية غير قابلة للتصرف |
| الإجراءات الخطرة تظهر أثرها وتحتاج تأكيدًا متناسبًا | `UX` + `SEC` | اختبار حذف/إلغاء/اعتماد/دفع | إجراء غير قابل للعكس بلا تحذير |
| الحقل المطلوب له سبب، وتقلل المدخلات اليدوية غير الضرورية | `UX` + `DATA` | مراجعة نموذج ووقت المهمة | جمع بيانات بلا استخدام معروف |
| اختبر المسار مع مستخدم ممثل أو Pilot عند ارتفاع المخاطر | `UX` + `PO` | ملاحظات واختبار نجاح مع حدود العينة | أخطاء حرجة متكررة أو اعتماد على الميسر |

### G4 — العربية والإنجليزية والمحتوى

| قائمة التحقق | المالك | دليل القبول | شرط التوقف |
| --- | --- | --- | --- |
| جميع النصوص ضمن نظام الترجمة ولا توجد سلاسل واجهة متروكة | `CONTENT` + `ENG` | فحص مفاتيح ومقارنة اللغتين | مفاتيح مفقودة أو نصوص مختلطة بلا قصد |
| المصطلح العربي مهني ومتسق مع قاموس متقن والسياق السعودي | `CONTENT` + `DOMAIN` | مراجعة مصطلحية | ترجمة حرفية تغير المعنى التشغيلي |
| RTL/LTR والأرقام والتواريخ والعملات والوحدات صحيحة | `CONTENT` + `UX` | لقطات واختبارات بيانات فعلية | انقلاب اتجاه أو قيمة مالية/زمنية خاطئة |
| الرسائل تشرح ما حدث وما الذي يفعله المستخدم تاليًا | `CONTENT` + `UX` | مراجعة microcopy وحالات الخطأ | رسالة تلوم المستخدم أو لا تقدم مخرجًا |
| العربية والإنجليزية متساويتان وظيفيًا، لا ترجمة لاحقة ناقصة | `PO` + `CONTENT` | parity checklist لكل رحلة | وظيفة أو مستند متاح بلغة واحدة دون قرار نطاق |
| أسماء الأدوار والحالات والتقارير متطابقة دلاليًا عبر المنتج | `CONTENT` + `DOMAIN` | glossary diff | تضارب مصطلحي يؤثر في القرار أو التدقيق |

### G5 — الوصول وإتاحة الاستخدام

المرجع الافتراضي للواجهات العامة والمنتج هو WCAG 2.2 مستوى AA حيث ينطبق.

| قائمة التحقق | المالك | دليل القبول | شرط التوقف |
| --- | --- | --- | --- |
| المهمة الأساسية قابلة بلوحة المفاتيح وبترتيب تركيز منطقي | `UX` + `ENG` | keyboard walkthrough | focus trap أو إجراء أساسي بالفأرة فقط |
| عناصر التحكم لها أسماء وحالات دلالية قابلة للقراءة | `ENG` | فحص accessibility tree وقارئ شاشة | زر/حقل بلا اسم أو حالة |
| التباين لا يقل عن الحد المطلوب للنص والعناصر غير النصية | `CRAFT` + `UX` | فحص آلي ويدوي للحالات كافة | مخالفة AA في مهمة أساسية |
| الخطأ لا يعتمد على اللون وحده ويرتبط بالحقل المعني | `UX` | form-error test | مستخدم لا يستطيع تحديد الخطأ |
| التكبير، reflow، reduced motion، واللمس مدعومة | `UX` + `ENG` | اختبار إعدادات النظام وأجهزة ممثلة | فقد محتوى أو تحكم بسبب التكبير/الحركة |
| الفحص الآلي يتبعه اختبار يدوي للمسار الحرج | `UX` | تقرير الأداتين | الاعتماد على نتيجة آلية فقط |

### G6 — الاستجابة والأداء والاعتمادية

| قائمة التحقق | المالك | دليل القبول | شرط التوقف |
| --- | --- | --- | --- |
| حدد أجهزة وشبكات وأحجام بيانات ممثلة قبل القياس | `ENG` + `UX` | performance profile | قياس على جهاز مطور فقط |
| لكل رحلة حرجة ميزانية زمن استجابة وحجم تحميل وخط أساس | `ENG` | قياس قبل/بعد وميزانية معتمدة | لا توجد ميزانية أو تراجع غير مفسر |
| الواجهة العامة تحقق أهداف Core Web Vitals المعتمدة للنسخة | `ENG` | قياس p75 من بيئة ممثلة أو RUM | فشل مستمر بلا قرار معالجة |
| الجداول والبحث والتقارير تختبر بحجم بيانات واقعي وحدود قصوى | `ENG` + `DATA` | fixture حجمي وquery plan عند الحاجة | timeout أو تحميل غير محدود |
| الجوال ونقاط التوقف المدعومة تختبر فعليًا بالعربية والإنجليزية | `UX` | device/browser matrix | إخفاء إجراء أو تداخل محتوى |
| الشبكة البطيئة والفشل الجزئي وإعادة المحاولة لا تفقد الإدخال | `ENG` | throttle/offline/error test | فقد بيانات أو تكرار غير مرئي |
| المراقبة تميز الخطأ البطيء من الخطأ الصريح | `OPS` | dashboard/alert evidence | عطل لا يمكن اكتشافه أو تشخيصه |

لا يحدد رقم أداء اعتباطيًا لكل الرحلات. يسجل الهدف قبل التنفيذ من احتياج
المهمة وخط الأساس، ويمنع الإطلاق عند تجاوزه ما لم يعتمد استثناء مؤقت ومؤرخ.

## 7. بوابة Staging

لا ينتقل التغيير إلى Staging إلا بعد اكتمال G1–G13 حسب النطاق، ووجود commit
نظيف قابل للمراجعة. بعد النشر على Staging يجب إثبات الآتي:

| قائمة التحقق | المالك | دليل القبول | شرط التوقف |
| --- | --- | --- | --- |
| مرجع Staging مستقل ولا يحتوي بيانات عميل Production | `REL` + `SEC` | project ref + isolation query قبل أول SQL | ref غير متحقق أو بيانات عميل |
| Git SHA، build، migrations، env-name inventory متطابقة مع المرشح | `REL` | deployment/ledger/checksum report | SHA/ref/checksum mismatch |
| الأسرار خاصة بالفرع ولا تستخدم مفاتيح Production | `SEC` + `REL` | masked inventory واختبار endpoint | أي اعتماد Production |
| migration replay ينجح على PostgreSQL 17 من التاريخ المعتمد | `ENG` + `DATA` | clean replay log | تاريخ ناقص أو تعديل migration مطبقة |
| fixtures حقيقية للأدوار والحالات السلبية والتزامن | `SEC` + `ENG` | test run بالأدوار المتوقعة | metadata assertions فقط لمسار P0 |
| المسارات الحرجة تعمل من المتصفح/API وقاعدة البيانات | `UX` + `ENG` | end-to-end evidence | اختلاف بين الواجهة والسلطة الفعلية |
| العربية/الإنجليزية والجوال/سطح المكتب والمستندات اجتازت QA | `UX` + `CONTENT` + `CRAFT` | test matrix | عطل يحجب مهمة أساسية |
| الرصد والتنبيه والدعم والتراجع جُربت | `OPS` | rehearsal evidence | لا كشف أو لا تراجع |
| جميع العيوب مصنفة بمالك وقرار، ولا P0/P1 مفتوح | `PO` + `REL` | defect ledger | P0 أو P1 أو خطر غير مصنف |

### مجموعة الخصوم الدنيا للمسارات ذات السلطة

- anonymous؛
- مستخدم authenticated عادي؛
- مستخدم غير نشط/موقوف؛
- Tenant A ضد Tenant B؛
- tenant admin؛
- platform admin؛
- service role؛
- إدخال معدل من العميل؛
- إعادة المحاولة والتزامن؛
- مرجع دفع مكرر ومتعارض؛
- الوصول المباشر والمسار غير المباشر/trigger حيث ينطبق.

## 8. بوابة Production

بوابة Production مراجعة قرار وليست إجراءً تلقائيًا. قبل أول تغيير إنتاجي:

| قائمة التحقق | المالك | دليل القبول | شرط التوقف |
| --- | --- | --- | --- |
| هوية المشغل والتفويض والنافذة وwrite freeze موثقة | `REL` + `PO` | approved runbook | لا تفويض أو هوية مبهمة |
| backup منطقي جديد مؤرخ، له حجم وSHA-256، واستعادة مقروءة | `OPS` | backup/restore report | backup قديم أو غير مستعاد |
| Git tag/SHA النهائي نظيف ومراجع ومتاح للمشغل | `REL` | immutable ref | worktree متسخ أو ref محلي مفقود |
| migration delta والترتيب والchecksums مطابقة لما اختبر على Staging | `ENG` + `DATA` | production read-only comparison | ledger مفاجئ أو checksum mismatch |
| Production env يشير فقط إلى موارد Production والأسماء المطلوبة موجودة | `REL` + `SEC` | masked inventory + deployed bundle check | Staging ref أو متغير لازم مفقود |
| Auth/SMTP/domain/payment/webhooks/cron جاهزة بالترتيب المعتمد | `OPS` + `ENG` | provider readiness evidence | اعتماد خارجي غير مثبت |

| cleanup للبيانات التجريبية منفصل ومحدد ويحتاج تفويضًا صريحًا | `PO` + `DATA` | preserve/delete classification | حذف ضمني أو غير محدد النطاق |
| لا يبدأ نشر التطبيق قبل جاهزية اعتمادات قاعدة البيانات والخدمات | `REL` | dependency order | تطبيق يعتمد على schema/config غير جاهز |

| نافذة مراقبة ومقاييس rollback محددة مسبقًا | `OPS` | monitoring plan | لا مالك بعد النشر |

## 9. شروط التوقف العامة

يوقف الترقية أو النشر فورًا عند أي من الآتي:

- اختلاف Git SHA أو tag أو migration checksum أو ledger عن المرشح المعتمد؛
- تعذر تحديد البيئة أو وجود مرجع Staging في Production أو العكس؛
- توسع صلاحيات غير مقصود أو fail-open أو وصول عابر للمؤسسات؛
- قدرة anonymous أو مستخدم موقوف على تنفيذ إجراء غير مصرح؛
- تسرب سر أو token أو PII أو أصل عميل غير مصرح؛
- فشل migration أو backup أو restore أو خطة الرجوع؛
- فساد، فقد، ازدواج، أو تعارض صامت في البيانات أو الدفع؛
- فشل التسجيل/OTP/login/provisioning أو مهمة تشغيلية إلزامية؛
- اختلاف التقرير أو المستند عن سجل النظام؛
- عائق وصول أو لغة أو استجابة يمنع دورًا مستهدفًا من إكمال مهمته؛
- ادعاء «معتمد/مطابق/الأفضل» لا يملك دليلًا صالحًا ونطاقًا واضحًا؛
- P0 أو P1 مفتوح، أو عيب غير مصنف في مسار حرج؛
- عدم وجود مشغل، مالك دعم، مراقبة، أو تراجع للتغيير؛
- أي تغيير إنتاجي خارج التفويض والنافذة المحددين.

يكتب سبب التوقف، أثره، المالك، والدليل المطلوب للإغلاق. لا يحول شرط توقف
إلى «مقبول» شفهيًا.

## 10. الاستثناءات وقبول المخاطر

1. `N/A` يحتاج سببًا محددًا واسم المراجع؛ لا يكفي «غير مطلوب».
2. لا استثناء من العزل، سرية الأسرار، سلامة الدفع، checksum التاريخ، أو منع
   الادعاء الزائف.
3. لا يؤجل P0. يجوز تأجيل P1 فقط بقرار مكتوب من `PO` و`SEC/OPS` حسب المجال،
   مع تخفيف مؤقت وموعد انتهاء وشرط إيقاف.
4. الاستثناء لا يصبح سابقة دائمة؛ يعاد تقييمه عند تغير النطاق أو البيانات أو
   البيئة أو المعيار.
5. من نفذ التغيير لا يعتمد وحده استثناءه عالي الخطورة.

## 12. قاعدة القرار النهائية

الاكتمال المهني ليس متوسط درجات. نجاح الحرفة لا يعوض فشل السلطة، ونجاح الأمن
لا يعوض غياب القيمة، وجمال التقرير لا يعوض بيانات غير موثوقة. إذا فشلت بوابة
إلزامية واحدة، فالحالة هي `NOT DONE` إلى أن يغلق الفشل بدليل صالح.
