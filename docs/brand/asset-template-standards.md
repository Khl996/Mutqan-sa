# Mutqan Asset & Template Standards

## Purpose
This document defines the standards for Mutqan sales, marketing, documentation, social, and demo assets.

It ensures that every external and internal asset communicates Mutqan consistently as a serious operational platform, not a generic CMMS or simple ticketing tool.

## Asset philosophy
Every Mutqan asset must answer three questions:

1. What operational problem are we addressing?
2. How does Mutqan connect the work, asset, location, evidence, report, or decision?
3. What proof, example, or next step makes the value clear?

If an asset does not answer these questions, it should be simplified or rejected.

## Core asset principles

### 1. Show transformation, not only features
Do not build assets around feature lists only.

Weak asset structure:
- Work orders.
- Assets.
- PM.
- Reports.
- Inventory.

Better asset structure:
- Before: scattered requests, missing asset history, unclear follow-up.
- With Mutqan: work connects to asset, location, team, evidence, and reports.
- After: clearer follow-up, stronger records, better operational review.

### 2. Use operational stories
Every asset should, when possible, use a scenario:

Request → Location → Asset → Work Order → Execution → Proof → Asset Record → Report → Decision

This story is the central narrative of Mutqan.

### 3. Evidence over promise
Do not use assets to imply capabilities that are not implemented.

Allowed:
- Roadmap language.
- Conceptual future direction.
- “Prepared for” or “designed to evolve toward” when accurate.

Avoid:
- Presenting AI, IoT, BIM, or Digital Twin as current features unless implemented.
- Showing visuals that imply integrations that do not exist.
- Claiming predictive maintenance without supporting functionality.

### 4. One brand, multiple contexts
Assets may adapt to different contexts, but the visual and verbal system should remain consistent.

Contexts:
- Facility management companies.
- Operations and maintenance teams.
- Residential and commercial compounds.
- Asset-heavy organizations.
- Multi-site facilities.
- Internal product documentation.
- Customer onboarding.

The message may change. The brand system should not fragment.

## One-page PDF standard

A Mutqan one-page PDF should include:

1. Clear headline.
2. The operational problem.
3. Mutqan's solution in one sentence.
4. Operating flow visual.
5. 3–5 value points.
6. Who it is for.
7. What the demo or pilot includes.
8. Clear call to action.

### Recommended sections

#### 1. Headline
Example:
> Turn scattered maintenance work into traceable operational memory.

Arabic:
> حوّل أعمال الصيانة المتفرقة إلى ذاكرة تشغيلية واضحة.

#### 2. Problem
Show real O&M friction:
- Requests in messages.
- Follow-up by calls.
- Assets without history.
- Reports without next action.

#### 3. Solution
Explain Mutqan as a connected operating platform.

#### 4. Operating flow
Use:
Request → Location → Asset → Work Order → Proof → Report → Decision

#### 5. Values
Examples:
- Clearer work follow-up.
- Asset history.
- Better accountability.
- Operational reporting.
- Pilot-ready implementation.

#### 6. CTA
Example:
> Request a demo.

## Sales deck standard

A standard Mutqan sales deck should follow this structure:

1. The operational problem.
2. Why WhatsApp, Excel, and memory are not enough.
3. Mutqan positioning.
4. Journey from request to decision.
5. Work orders in context.
6. Asset memory and Asset Passport concept.
7. Proof of Work.
8. Reports and Decision Brief.
9. Controlled Pilot scope.
10. Pricing or next step, when appropriate.

## Demo story script standard

A Mutqan demo should not be a tour of pages.

It should be a story:

1. A maintenance request appears.
2. It is tied to a location.
3. It is tied to an asset.
4. It becomes a work order.
5. A technician executes it.
6. Evidence is captured.
7. The work is reviewed or approved.
8. The asset record is updated.
9. The report reveals what needs attention.
10. The manager sees a decision point.

## Product screenshot standard

Do not use raw screenshots without explanation.

Each screenshot should include:
- Value headline.
- Highlight or annotation.
- Short caption.
- Operational context.

### Example
Weak:
> Work orders screen.

Better:
> See overdue work by location, asset, and responsible team before delays become invisible.

## LinkedIn template standard

Mutqan LinkedIn visuals should be educational, practical, and operational.

Approved content series:

### 1. Not every closure is achievement
Theme: Closing a work order is not enough if the root issue repeats.

### 2. Every asset has a story
Theme: Asset memory, maintenance history, and operational decisions.

### 3. Where operations get lost
Theme: WhatsApp, Excel, scattered reports, and personal memory.

### 4. From number to decision
Theme: Reports should explain what needs attention.

### 5. Field reality
Theme: What technicians, supervisors, and maintenance managers actually need.

### 6. Building Mutqan transparently
Theme: Product thinking, lessons, and operational philosophy.

## Pilot offer material standard

Pilot materials should clearly define:

1. Duration.
2. Scope.
3. Included setup.
4. Included training.
5. What is not included.
6. Success metrics.
7. Weekly review rhythm.
8. End-of-pilot value report.
9. Conversion path.

Avoid open-ended pilot promises.

## Customer onboarding asset standard

Onboarding assets should be role-based.

Required future quick cards:

### Technician quick card
- See my tasks.
- Start work.
- Add note/photo.
- Use parts if needed.
- Complete work.

### Supervisor quick card
- Review assigned work.
- Approve or reject.
- Return with reason.
- Monitor delays.

### Maintenance manager quick card
- Review open and overdue work.
- Check critical assets.
- Review PM status.
- Read weekly brief.

### Tenant admin quick card
- Add users.
- Set roles.
- Configure locations.
- Review modules/settings.

## Documentation standard

Documentation should be:
- Practical.
- Short.
- Role-based.
- Scenario-based.
- Supported by screenshots when needed.
- Written in operational language.

Avoid documentation that only explains menus.

Better:
- How to create a work order from a real request.
- How to complete a task as a technician.
- How to review delayed work as a supervisor.
- How to read asset history.
- How to prepare for a weekly operations review.

## Proposal standard

A proposal should include:

1. Customer context.
2. Observed operational pain.
3. Proposed Mutqan starting scope.
4. Pilot or subscription scope.
5. What is included.
6. What is excluded.
7. Timeline.
8. Responsibilities.
9. Price.
10. Next step.

Do not use generic proposals when the customer's operational context is known.

## Visual asset rules

### Do
- Use Mutqan brand colors and tokens.
- Use connected flow visuals.
- Use operational examples.
- Use clear Arabic and English typography.
- Use calm layouts.
- Use screenshots with meaning.
- Use diagrams that explain relationships.

### Do not
- Use random maintenance stock images as the main identity.
- Overload assets with icons and buzzwords.
- Use AI-like visuals unless the feature is actually related and framed correctly.
- Mix illustration styles.
- Create one-off designs that cannot be repeated.
- Make each asset feel like a different company.

## Asset approval checklist

Before publishing or sending any asset, ask:

1. Is the operational problem clear?
2. Is Mutqan's role clear?
3. Is there a real example or scenario?
4. Does it avoid overpromising?
5. Does it use approved visual language?
6. Is the CTA clear?
7. Can a new employee reproduce this style?
8. Does it strengthen trust?
