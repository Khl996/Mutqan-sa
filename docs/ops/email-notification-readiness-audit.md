# فحص جاهزية إشعارات البريد في متقن

الحالة: فحص فني وتشغيلي  
المالك: المؤسس  
المشغل التنفيذي: Codex  
آخر تحديث: 2026-05-01

## 1. القرار

البريد الإلكتروني هو قناة الإشعارات الرسمية المعتمدة حاليا في متقن.

واتساب يبقى مسارا مستقبليا أو اختياريا لاحقا، ولا يعتمد كقناة تشغيل رسمية الآن.

## 2. نتيجة الفحص

الحكم قبل الإصلاح:

البريد لا يعمل فعليا في الوضع المنشور الحالي.

السبب المباشر:

دالة Supabase Edge Function باسم `resend-email` منشورة بإعداد `verify_jwt = true`، بينما استدعاء قاعدة البيانات من `pg_net` يرسل السر الداخلي `x-internal-email-secret` فقط ولا يرسل Authorization JWT.

لذلك الطلب يفشل قبل دخول كود الدالة.

الحكم بعد الإصلاح بتاريخ 2026-05-01:

تمت إعادة نشر `resend-email` بإعداد `verify_jwt = false` لهذه الدالة فقط، مع بقاء التحقق من السر الداخلي داخل الكود.

النتيجة الحالية:

مسار قاعدة البيانات أصبح يستطيع الوصول إلى كود الدالة. لم يتم إرسال بريد حقيقي بعد، لذلك حالة Resend النهائية تحتاج اختبار إرسال داخلي واحد.

## 3. مسار الإرسال الحالي

المسار الحالي:

1. يتم إنشاء صف في جدول `notifications`.
2. Trigger باسم `trg_send_email_on_notification` يعمل بعد الإدخال.
3. الدالة `send_email_notification()` تقرأ بريد المستخدم من `auth.users`.
4. الدالة تقرأ:
   - `app.resend_email_url`
   - `app.resend_email_secret`
5. ترسل طلب HTTP عبر `net.http_post`.
6. الطلب يفترض أن يصل إلى Edge Function `resend-email`.
7. Edge Function ترسل البريد عبر Resend.

## 4. الأدلة

### التريغر موجود ومفعل

جدول `notifications` لديه Trigger:

`trg_send_email_on_notification`

ويعمل على:

`AFTER INSERT`

وينفذ:

`send_email_notification()`

### الأسرار موجودة

الأسرار التالية موجودة في قاعدة البيانات:

- `app.resend_email_url`
- `app.resend_email_secret`

الرابط يشير إلى:

`/functions/v1/resend-email`

ولم يتم كشف قيمة السر في الفحص.

### الدالة كانت منشورة لكنها تتطلب JWT

Edge Function:

| الدالة | الحالة | verify_jwt |
| --- | --- | --- |
| resend-email | ACTIVE | true |

بعد الإصلاح:

| الدالة | الحالة | الإصدار | verify_jwt |
| --- | --- | ---: | --- |
| resend-email | ACTIVE | 11 | false |

### نتيجة آخر استدعاءات البريد

آخر ردود `net._http_response` أظهرت:

| التاريخ | status_code | العدد | العينة |
| --- | ---: | ---: | --- |
| 2026-04-30 | 401 | 9 | Missing authorization header |

هذا يثبت أن القناة لا تصل إلى منطق Resend أصلا.

### اختبار آمن بعد الإصلاح

تم إجراء اختبار تفويض بسر خاطئ عمدا حتى لا يرسل بريد حقيقي.

النتيجة:

| الطلب | status_code | الرد |
| --- | ---: | --- |
| اختبار تفويض بدون إرسال | 401 | Unauthorized |

هذه نتيجة صحيحة بعد الإصلاح، لأنها تثبت أن الطلب وصل إلى كود الدالة، وأن الدالة رفضته بسبب السر الخاطئ. الخطأ السابق من بوابة Supabase لم يعد يظهر.

## 5. الإصلاح المطلوب

تم تنفيذ إعادة نشر Edge Function `resend-email` مع تعطيل JWT verification لهذه الدالة تحديدا، لأن الحماية الداخلية تعتمد على الهيدر:

`x-internal-email-secret`

الأمر المنفذ:

```powershell
npx supabase functions deploy resend-email --project-ref <YOUR_SUPABASE_PROJECT_REF> --no-verify-jwt --use-api
```

هذا لا يلغي الحماية كلها، لأن كود الدالة ما زال يرفض أي طلب لا يحمل السر الداخلي الصحيح.

## 6. فحص بعد الإصلاح

بعد إعادة النشر، نفحص:

1. تم: `resend-email` يظهر `verify_jwt = false`.
2. متبق: إنشاء إشعار اختبار آمن لمستخدم داخلي فقط.
3. متبق: فحص `net._http_response` يجب أن يظهر `200` أو رد Resend واضح.
4. متبق: التأكد من وصول البريد للعنوان الداخلي.
5. إذا فشل Resend، نفحص `RESEND_API_KEY` أو تحقق الدومين `facility-management.space`.

## 7. لماذا لم نرسل اختبار الآن

لم يتم إرسال اختبار بريد حقيقي أثناء هذا الفحص.

السبب:

- إنشاء إشعار اختبار سيرسل إلى مستخدم حقيقي بعد الإصلاح.
- الاختبار الآمن استخدم سرا خاطئا عمدا لإثبات الوصول للدالة بدون إرسال بريد.
- اختبار الإرسال الفعلي يحتاج عنوانا داخليا معتمدا أو موافقة صريحة على إرسال رسالة اختبار.

## 8. مخاطر قبل التفعيل

قبل تفعيل البريد فعليا يجب الانتباه إلى:

- وجود تضخم سابق في الإشعارات بتاريخ 2026-04-25.
- كل إشعار داخلي قد يتحول إلى بريد.
- لا يوجد حاليا جدول تسليم منفصل يوضح نجاح/فشل كل قناة.
- تفضيلات المستخدم موجودة في الواجهة، لكنها ليست مستخدمة بوضوح داخل تريغر البريد الحالي.

## 9. التوصية التنفيذية

الترتيب الآمن:

1. اعتماد الإيميل كالقناة الرسمية الحالية.
2. إعادة نشر `resend-email` باستخدام `--no-verify-jwt`.
3. تشغيل اختبار داخلي واحد.
4. تعديل منطق البريد لاحقا ليحترم تفضيلات المستخدم `notification_preferences.email`.
5. إضافة جدول تسليم `notification_deliveries` قبل التوسع.

بهذا يصبح البريد قناة حقيقية يمكن قياسها، بدل أن يكون تريغر موجودا نظريا فقط.
