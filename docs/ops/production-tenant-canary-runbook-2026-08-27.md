## 1. قواعد غير قابلة للتجاوز

- Staging يسبق Production، ويجب أن يثبت الهجرات والواجهة والرحلة المستضافة نفسها.
- واجهة جسر الحوكمة المصغرة أولًا، ثم قاعدة البيانات، ثم مرشح Vercel مطفأ للجميع، ثم إنشاء المستأجر، ثم التفعيل. الجسر ليس نشرًا للرحلة الجديدة؛ هو طبقة توافق أمنية تعمل قبل وبعد P0.
- الأمن وإصلاحات السلطة عالمية؛ ظهور الرحلة الجديدة فقط هو المقيد بعلم المستأجر.
- قيمة مفقودة أو خطأ أو استجابة مشوهة أو عدم تطابق المستأجر تعني `false`.
- لا `migration repair`، ولا `--include-all`، ولا `--include-seed`، ولا SQL يدوي خارج الهجرات المجمّدة.
- لا إنشاء عبر التسجيل العام. إنشاء المستأجر والحسابات يتم بمسار إداري مصادق ومدقق.
- لا حذف أعمى. الإيقاف والتعليق والهجرة التعويضية هي مسارات التراجع المقبولة.
- قرار المؤسس في 2026-09-05: تأجيل تغيير كلمة مرور قاعدة البيانات إلى ما بعد استكمال العمل. لم يعد التدوير شرط إيقاف لهذا التنفيذ؛ يبقى إجراءً لاحقًا، مع إدخال الاعتماد الحالي عبر prompt مخفي وعدم حفظه في المصدر أو التقارير. بقية بوابات النسخ والاستعادة والعزل ثابتة.

## 2. إثبات Staging الإلزامي

أوقف المهمة ما لم تنجح العناصر التالية على مشروع Staging المستقل:

1. تثبيت commit/tag واحد، وبصمات SHA-256 للهجرات والاختبارات والبناء.
2. تطبيق سلسلة Wave 0/P0 المقبولة، ثم:
   - `20260824180500_p0_work_order_proof_authority.sql`؛
   - `20260826230345_tenant_release_control.sql`؛
   - `20260828084500_tenant_governance_authority_bootstrap.sql`.
3. إثبات أن `operations_golden_path_v1` مطفأ افتراضيًا لكل المستأجرين.
4. إثبات أن دالة القراءة الوحيدة للواجهة هي:
   `public.get_my_tenant_release_flag(p_flag_key text)`، للمصادق فقط، ومن دون قبول `tenant_id` من العميل.
5. إثبات أن التفعيل لا يتم إلا بواسطة `postgres` عبر:
   `internal.set_tenant_release_flag(uuid,text,boolean,text,text,uuid)`، وأن `PUBLIC` و`anon` و`authenticated` و`service_role` لا يملكون تنفيذها.
6. إثبات أن كل مستأجر جديد يحصل ذريًا على أدوار الحوكمة الافتراضية الخمسة، وأن فشل التهيئة يُرجع إنشاء المستأجر كله.
7. تفعيل العلم لمستأجر Staging صناعي واحد، ثم نجاح رحلة البلاغ → تقييم الحوكمة → الاعتماد → التنفيذ → المراجعة → الإغلاق → snapshot v2 → إثبات الإنجاز بالعربية والإنجليزية.
8. رفض المستخدم الموقوف، والمحاولة العابرة للمستأجر، وتسريب الدوال للمجهول، وأي كتابة مباشرة في snapshot أو PDF metadata أو `operation_logs`.
9. إطفاء العلم مجددًا وإثبات الرجوع إلى المسار القديم من دون flash للواجهة الجديدة أو طلب بيانات إثبات خاصة بها.
10. تطبيق `20260903235032_p0_explicit_api_function_publication.sql` وإثبات أن أي دالة `public` جديدة مملوكة لـ`postgres` مرفوضة لـ`PUBLIC` و`anon` و`authenticated` و`service_role` حتى تُنشر بـ`GRANT` صريح، مع بقاء قائمة المجهول الخماسية كما هي.

## 3. بوابات STOP على الإنتاج

يجب تسجيل نتيجة كل بوابة في سجل التغيير. توقف فورًا إذا لم تتحقق كلها:

| البوابة | شرط المرور |
|---|---|
| الهوية | المرجع المستهدف هو مشروع Production المعتمد، وليس Staging، ومثبت بواسطة مشغلين اثنين |
| المصدر | commit/tag نظيف ومجمّد؛ لا يدخل `supabase/.temp` أو أي ملف غير مقصود |
| سجل الهجرات | القراءة الحية تطابق خط الأساس؛ لا نسخة مفقودة أو زائدة أو مكررة |
| الخطة الجافة | تعرض فقط الهجرات المراجعة وبترتيبها؛ أي اختلاف يوقف المهمة |
| التزامن | مشغل قاعدة واحد، ولا توجد كتابة schema متزامنة أو نشر تلقائي غير مضبوط |
| التراجع الآمن | قبل DB: الرجوع لنسخة Vercel الحالية. بعد DB: الرجوع إلى جسر الحوكمة المتوافق مع إطفاء Canary. خلل القاعدة يُصحح بهجرة forward-only مراجعة ولا يُعالج بإعادة واجهة قديمة غير متوافقة أو بإضعاف السلطة |
| نسخ Vercel | deployment ID وcommit ووقت البناء مسجلة للنسخة الحالية وجسر الحوكمة والمرشح؛ هدف rollback بعد DB هو الجسر وليس SHA القديم |
| ربط الجدولة والأسماء | لا يُعد `--skip-domain` عزلًا لـCron أو لاسم المشروع الافتراضي. تُفحص الأسماء الثلاثة و`targets.production` و`crons.deploymentId` وhost وحالة الجدولة والمساران/التوقيتان بشكل مستقل؛ أي اختلاف غير مقصود يوقف الانتقال |
| النسخ الاحتياطي | recovery point حديث + logical backup جديد ومكتمل + restore ناجح ومعزول + عهدة مفتاح مستقلة |
| التوافق | جسر الحوكمة ينجح قبل P0 وبعده، والمرشح يعمل مع flags-off. النسخة `7eb34b2` ليست هدف rollback مقبولًا بعد P0 لأنها لا تملك مسار تقييم/اعتماد الحوكمة |
| العزل | المجهول، المستخدم الموقوف، ومحاولة مستأجر A ضد B مرفوضة؛ لا توسع صلاحيات |
| التحكم | مستأجر Control قائم ومختار للقراءة والمقارنة فقط، من دون أي تغيير أو بيانات شخصية في التقرير |

## 4. النسخة الاحتياطية قبل أي DDL

1. تحقق من أحدث Daily Backup أو PITR recovery point وسجّل توقيته وحالته.
2. أنشئ فورًا نسخة منطقية مشفرة وخارج المستودع تشمل:
   - الأدوار؛
   - schema؛
   - البيانات؛
   - schema وبيانات `supabase_migrations`.
3. سجّل SHA-256 والحجم ووقت البداية والنهاية لكل ملف، من دون تسجيل connection strings أو كلمات مرور.
4. استعد النسخة إلى مشروع/قاعدة معزولة باستخدام transaction و`ON_ERROR_STOP`، ثم قارن ledger، وعدد الجداول، والدوال الحرجة، وRLS، وعدد الصفوف الإجمالي المتوقع.
5. سجّل inventory لمفاتيح `work-order-pdfs`. نسخة قاعدة البيانات تحفظ metadata ولا تحفظ ملفات Storage نفسها؛ هذه المهمة لا تحذف تلك الملفات.

تمرين 2026-09-05 موثق في [إثبات تمرين النسخة المنطقية للإنتاج](./production-logical-backup-rehearsal-2026-09-05.md). نتيجته `PASS`، لكنه ليس النسخة النهائية لنافذة DDL.

الأمر المفضل للنسخة النهائية، من جذر المرجع المجمد وباستخدام PowerShell 7، هو الوضع اليدوي بعبارة عشوائية منشأة ومحفوظة مسبقًا في vault معتمد:

```powershell
pwsh -NoProfile -File .\scripts\Invoke-ProductionLogicalBackupGate.ps1
```

يمكن استخدام `-GenerateProtectedPassphrase` في التمرين؛ يولد 48 byte عشوائية ويحفظها في ملف Windows DPAPI `CurrentUser` منفصل مع ACL للمشغل فقط. لا يُقبل هذا الوضع لنافذة DDL حتى تُنشأ عهدة مستقلة خارج الجهاز/ملف المستخدم.

تُدخل كلمة مرور قاعدة Production وعبارة التشفير داخل الطرفية المخفية فقط، ولا تُرسل في المحادثة أو تُحفظ في Git. يجب حفظ عبارة التشفير في مخزن أسرار منفصل؛ فقدها يجعل النسخة غير قابلة للاستعادة. النجاح المقبول وحده هو ظهور `PRODUCTION LOGICAL BACKUP GATE: PASS` بعد manifest وبصمات SHA-256 ومطابقة source/restore inventory.

نفّذ فحصًا مستقلًا في عملية جديدة على manifest الناتج:

```powershell
pwsh -NoProfile -File .\scripts\Test-ProductionLogicalBackupArtifact.ps1 `
  -ManifestPath '<absolute-path-to-manifest.json>'
```

لا تقبل البوابة ما لم يثبت الفاحص `inventory_match=true` و`independent_dpapi_decrypt=true` أو ما لم تُثبت عبارة vault اليدوية فك الأثر ومطابقة decrypted SHA-256. الأداة اختُبرت من البداية للنهاية على مصدر PostgreSQL 17 معزول، واختُبر مسار الفشل للتأكد من عدم بقاء key أو manifest نجاح زائف.

تغيير كلمة مرور قاعدة Production مؤجل بقرار المؤسس في 2026-09-05. عند التغيير لاحقًا، سجّل نجاح اتصال جديد من prompt مخفي وتحقق من أي خدمة خارجية تستخدم connection string مباشر؛ خدمات Supabase المدارة تُحدّث داخليًا، لكن الاتصالات الخارجية تحتاج مراجعة.

فحص المصدر المتتبع في Git بتاريخ 2026-09-05، قراءة فقط، قارن المرشح `1a148e4507f4cd110f8605ee03f7b827ae56bb63` بالنسخة المنشورة `7eb34b25f960571837b6be5b227508b907311c7f` وخلص إلى الآتي:

- لا يستخدم runtime في أي منهما `DATABASE_URL` أو `SUPABASE_DB_URL` أو متغيرات `PG*` أو مكتبة عميل PostgreSQL مباشر؛ الاتصال التطبيقي يتم عبر `@supabase/supabase-js` باستخدام URL ومفاتيح Supabase.
- لا يعرّف `vercel.json` اتصال قاعدة مباشر. قائمة أسماء متغيرات runtime المستخرجة من المصدر لا تحتوي كلمة مرور قاعدة البيانات.
- تحتوي النسخة المنشورة أثر CLI قديمًا في `supabase/.temp/pooler-url` يشير إلى مشروع Production من دون مكوّن كلمة مرور، ولا يوجد ملف tracked يستورده أو يقرأه؛ وهو غير موجود في المرشح الحالي.
- لذلك لا يظهر من الكود أو إعداد Vercel المتتبع أن تدوير كلمة مرور قاعدة البيانات يتطلب تغيير التطبيق. هذا لا يغطي الأجهزة المحلية، أسرار CI غير المتتبعة، أدوات المشغل، أو خدمات طرف ثالث؛ يجب أن يؤكد المشغل جردها قبل التدوير.
- إذا وُجد عميل مباشر بالقيمة القديمة، أوقفه وحدّثه قبل التدوير ولا تسمح بمحاولات متكررة بكلمة قديمة؛ فالمحاولات المتكررة قد تفعّل حظر Supavisor المؤقت.

عدم نجاح الاستعادة يعني أن النسخة غير مقبولة ويمنع أي هجرة إنتاجية.

## 6. إنشاء المستأجر وحساباته

بعد نجاح نشر flags-off فقط:

1. اقرأ الخطط النشطة واعتمد plan code صريحًا للاختبار؛ لا تعتمد على افتراض أو سعر تجاري غير معتمد.
2. أنشئ حساب الاختبار عبر المسار الإداري المصادق مع `registration_draft` للاسمين `Mutqan Canary Lab` و`مختبر متقن التجريبي`؛ لا تُرسل كلمة المرور إلى سجل أو Git.
3. أثبت أن `complete_pending_registration` مرفوض قبل الاعتماد، ثم أصدر اعتمادًا أحادي الاستخدام من platform admin بالخطة المعتمدة.
4. من جلسة الحساب نفسه نفّذ `complete_pending_registration`، وتحقق من:
   - الدور `tenant_admin`؛
   - تجربة مشتقة من الخطة، لا من مدخل العميل؛
   - tenant واشتراك واحد فقط؛
   - slug مولّد `mutqancanarylab`؛
   - العلم ما زال مطفأ؛
   - خمسة حدود حوكمة افتراضية: `supervisor` و`engineer` و`facility_manager` و`maintenance_manager` و`tenant_admin`.
5. أعد `complete_pending_registration` وتحقق أنه يعيد المستأجر نفسه، ثم أثبت أن محاولة `provision_tenant` ثانية مباشرة مرفوضة.
6. أنشئ عبر `/api/admin-manage-user` المحمي بقية حسابات `maintenance_manager` و`supervisor` و`engineer` و`technician` و`reporter` بعناوين بريد اختبار تملكها متقن وكلمات مرور مؤقتة قوية. لا تُخزن بيانات الدخول في Git أو التقرير.
7. إذا فشل إنشاء مستخدم، علّق المستأجر والحسابات التي أُنشئت وسجّل الحالة للاستعادة؛ لا تحذف المستأجر تلقائيًا.

## 7. التفعيل للمستأجر وحده

1. اقرأ العلم من جلسة المستخدم وتأكد أن النتيجة `false` قبل التفعيل.
2. من جلسة قاعدة بيانات بدور `postgres` فقط، استدعِ:
   `internal.set_tenant_release_flag(<tenant_id>, 'operations_golden_path_v1', true, <reason>, <actor_label>, <actor_user_id>)`.
3. يجب أن يعيد `true` عند التغيير الفعلي، ويكتب حدث audit ذريًا. إعادة الطلب نفسها يجب أن تكون no-op وتعيد `false`.
4. تحقق من أن `internal.tenant_release_flag_enabled(...)` صحيحة للمستأجر التجريبي فقط، وأن getter يعيد tenant الجلسة نفسه.
5. افتح جلسة جديدة لكل دور ونفّذ الرحلة الذهبية كاملة. لا تستخدم platform admin غير المرتبط بمستأجر لإثبات واجهة Canary؛ سلوكه المقصود Legacy.

## 8. المقارنة والمراقبة

قارن Canary مع مستأجر Control قبل التفعيل، وبعد 15 دقيقة، وبعد ساعتين، وبعد 24 ساعة:

- نسبة نجاح login والطلبات و`close_work_order`؛
- أخطاء Vercel 5xx وأخطاء Supabase/Auth وSQLSTATE الجديدة؛
- زمن تحميل أمر العمل وتوليد إثبات الإنجاز؛
- عدد snapshots v2 وسجلات الإغلاق، وعدم وجود ازدواج عند التزامن؛
- عدم وجود قراءة أو كتابة عابرة للمستأجرين؛
- عدم ظهور Proof UI أو طلباته في Control؛
- عدم وجود كتابة مباشرة إلى PDF metadata أو `operation_logs`؛
- سلامة PM والدفع والبوابة العامة والمهام المجدولة.

**STOP فوري:** أي تسريب بين المستأجرين، نجاح مجهول على دالة غير allowlisted، فقد/استبدال دليل، إغلاق مزدوج، زيادة مستمرة في 5xx، فشل Control في مسار كان يعمل، أو ledger/ACL drift.

## 9. الإيقاف والتراجع

1. **Kill switch أولًا:** استخدم setter نفسه كـ`postgres` مع `enabled=false` وسبب واضح، ثم أثبت رجوع Canary إلى Legacy.
2. **عزل الحسابات عند الحاجة:** عطّل profiles واحظر جلسات Auth عبر المسار الإداري؛ لا تعتمد على إخفاء الواجهة.
3. **خلل واجهة/API أو ربط Cron:** أوقف الجدولة أولًا. قبل DB استخدم النسخة الحالية المثبتة. بعد DB نفّذ التراجع إلى **جسر الحوكمة المسجل فقط**، ثم تحقق من الأسماء والـ5xx والرحلة المحكومة. التراجع عن النطاق وحده لا يعيد Cron؛ أعد ربطه بأثر متوافق عبر مسار Vercel المدعوم ثم افحص host وdeployment والسجلات قبل إعادة الجدولة. لا ترجع إلى `7eb34b2` بعد P0. [توثيق Vercel لسلوك Cron عند التراجع](https://vercel.com/docs/cron-jobs/manage-cron-jobs#rollbacks-with-cron-jobs).
4. **خلل قاعدة:** أوقف الكتابات المتأثرة، وطبّق هجرة تعويضية forward-only. لا تعدّل أو تحذف أو تعيد ترتيب migration مطبقة.
5. **حادث كارثي فقط:** استخدم PITR أو النسخة المنطقية بعد قرار توقف معلن؛ الاستعادة تعيد مشروع الإنتاج كله وقد تسبب downtime وفقد تغييرات أحدث.
6. احتفظ بالمستأجر التجريبي وبياناته وأحداث العلم كأدلة. الحذف يتطلب قرارًا مستقلًا ونطاقًا محددًا وخطة احتفاظ، وليس خطوة rollback.

## 10. قرار التوسيع

لا يُفعّل مستأجر ثانٍ حتى تمر نافذة 24 ساعة، وتكتمل رحلة الأدوار، وتكون نتائج Control سليمة، ولا يوجد P0/P1 مفتوح. التوسيع يتم مستأجرًا بعد مستأجر عبر setter نفسه؛ التعميم الشامل قرار إصدار منفصل.
